\section{System Design and Methodology}
\label{sec:methodology}

\subsection{Objectives and scope}

The design starts from explicit, machine-validated scenarios and uses container network stacks with standard Linux tools. Routing and impairment state are checked before measurements are trusted, and each run is expected to leave structured evidence. Extensions reuse this bounded execution path. The system is an experimental NDT, not a synchronized replica of an operational network; its claims concern controlled behaviour in the tested configurations.

Figure~\ref{fig:architecture} summarizes the execution path. A scenario/configuration enters validation before any topology is built. The validated representation drives Docker topology creation, routing and forwarding, impairment configuration, and measurement. Results are serialized as JSON and comma-separated value (CSV) files and accompanied where available by logs, summaries, statistics, and plots. Cleanup is scoped to project-owned resources so that a failed run does not justify broad container or network deletion.

\subsection{Scenario representation and validation}

Scenarios describe node roles, links, addressing, impairments, and traffic endpoints. The method follows a fixed chain: parse; validate schema, semantics, and bounds; build project-scoped Docker resources; configure and verify forwarding, routes, and qdiscs; run measurements; serialize metrics and logs; then remove run-scoped resources. Small experiments use allowlisted direct, routed, or two-router forms; the generic path supports larger graphs. AI-originated content also passes prompt constraints and projection, so it cannot choose commands, images, credentials, or host paths. Appendix~\ref{sec:implementation-specification} gives a valid scenario and the implemented checks.

\subsection{Docker topology and routing}

Docker containers attach to one deterministic network per link, and router containers enable forwarding. The generic path allocates point-to-point subnets, computes breadth-first shortest paths with deterministic tie-breaking, installs static routes, and checks the expected destination route before traffic. Appendix~\ref{sec:implementation-specification} specifies addressing, route scope, commands, and assumptions.

Germany50 extends this mechanism using imported Topology Zoo data. The normalized scenario contains 50 router nodes and 88 links with deterministic subnets. Two routing modes were retained. Selected mode installs the routes needed for the three representative endpoint pairs. Full mode generates the theoretical 4,224-entry plan, but the retained full-mode evidence is a dry-run validation only. This separation is fundamental: plan generation, route installation, and traffic exercise are distinct claims.

\subsection{Impairment and measurement pipeline}

Linux traffic control implements configured conditions. A token bucket filter (TBF) is used for bandwidth-only links; combined bandwidth and delay/loss use the implemented \texttt{netem rate} command, not the same TBF hierarchy. The framework checks qdisc state and runs ping and reverse-TCP iperf3. Ping supplies counts, loss, and RTT; iperf3 supplies throughput. Configured one-way conditions therefore remain separate from measured end-to-end quantities. Exact templates appear in Appendix~\ref{sec:implementation-specification}.

Each run writes its normalized scenario and metrics into a run-specific directory. Batch runners add manifests, per-run rows, summaries, environment records, and cleanup outcomes. Failed or retried attempts remain visible. Analysis assumes that retained tool output represents the container path exercised by its runner; it does not assume synchronized physical-network state, identical host timing, or unmeasured all-pairs reachability. The dissertation inventory distinguishes repository-reported values from statistics recomputed during a read-only audit.

\subsection{Automation extensions}

\paragraph{AI-assisted generation.} The AI path requests a structured scenario, validates it, projects it into the executable representation, and permits only dry-run or controlled execution. Provider identity is retained separately from validation outcome. The official OpenAI call and the OpenAI-compatible Qwen call are recorded as different evidence items.

\paragraph{Closed-loop control.} The RL extension uses a minimal dual-path Docker topology. Each episode observes measured state, selects and verifies a route, runs ping and iperf3, computes reward, and checkpoints the result. Q-learning is compared with a threshold heuristic and fixed A/B policies under one ordered two-phase schedule. Appendix~\ref{sec:rl-formulation} records the exact actions, state thresholds, reward, path conditions, hyperparameters, and seed.

\paragraph{Dashboard.} The reviewer-facing \path{dashboard/interactive_server.py} is a supporting interface, not the front end for every formal experiment. It permits dry-runs for direct, routed, and two-router scenarios; real Docker execution is restricted to direct topology, with routed and two-router requests rejected by both browser and server. It retains parameter bounds, restricted artifact downloads, and run-scoped cleanup. Germany50 and RL remain read-only results, and arbitrary Docker commands are not accepted.

\subsection{Reproducibility and security}

The sealed formal evidence contains versioned scenarios, runners, per-run metrics, summaries, figures, failures, and cleanup records. A later reviewer-readiness publication, GitHub main commit \texttt{5f0d4962c0340aa44dce04d4d1001eb2b7746d1b}, added \path{scripts/reviewer_setup.sh} and \path{scripts/reviewer_dashboard.sh}. From a fresh WSL clone, these create an isolated Python environment, install requirements, build \path{my-iperf-tc}, run the 69 unit tests, and start the interactive server; they do not invoke the formal delay, loss, bandwidth, Germany50, AI, or RL matrices. That software-validation state post-dates and does not alter the sealed experimental evidence. Exact timing remains host-sensitive because Docker shares its kernel and resources with the host. Appendix~\ref{sec:reviewer-reproduction} records the concise reviewer procedure and the evidence boundary.
