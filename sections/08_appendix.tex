\subsection{Implementation specification}
\label{sec:implementation-specification}

This compact JSON is valid under the generic project schema:

\begin{verbatim}
{"topology_name":"client-router-server",
 "addressing":{"base_cidr":"10.64.0.0/16","subnet_prefixlen":29},
 "nodes":[{"id":"client","type":"client"},
          {"id":"router","type":"router"},
          {"id":"server","type":"server"}],
 "links":[{"source":"client","target":"router",
           "bandwidth_mbps":20,"delay_ms":0,"packet_loss_percent":0},
          {"source":"router","target":"server",
           "bandwidth_mbps":20,"delay_ms":10,"packet_loss_percent":0}],
 "traffic":{"source":"client","destination":"server","protocol":"tcp",
            "duration_s":5,"ping_count":3,"reverse":true},
 "route_generation_mode":"traffic_endpoint_subnets"}
\end{verbatim}

\paragraph{Validation.} The generic path requires documented top-level fields; known link and traffic endpoints; rejection of duplicate undirected links and disconnected topologies; duplicate interface-address and route-conflict checks; non-negative delay; loss within 0--100\%; and positive bandwidth. The guarded AI schema is narrower: 2--10 nodes, lower-case identifiers beginning with a letter (maximum 32 characters), exactly one client and one server, TCP only, delay 0--250 ms, loss 0--20\%, bandwidth 1--1000 Mbps, duration 1--30 s, and ping count 1--10. It also rejects command/Internet Protocol (IP)-shaped strings, checks prompt constraints and connectivity, and projects only allowlisted fields.

\paragraph{Addressing and routing.} Generic execution uses \texttt{10.64.0.0/16} and assigns successive /29 point-to-point subnets. The bridge reserves the first usable address; link endpoints receive the next two. Breadth-first search with sorted neighbours generates deterministic shortest paths. Static routes target either all unattached subnets or traffic-endpoint subnets; equal-length candidates use lexicographic path order. Runtime verification executes \texttt{ip route show <destination>} and checks \texttt{<destination> via <next-hop>}. Germany50 selected mode covers retained endpoint paths; full mode is a generated dry-run plan.

\paragraph{Traffic control and measurement.} Bandwidth-only links execute:
\begin{verbatim}
tc qdisc replace dev <iface> root tbf rate <X>mbit \
  burst 32kbit latency 400ms
\end{verbatim}
For bandwidth combined with delay and/or loss, \texttt{build\_combined\_qdisc\_commands} instead emits one root \texttt{netem} command containing applicable \texttt{delay <D>ms}, \texttt{loss <L>\%}, and \texttt{rate <X>mbit} terms. Impairment-only links use root \texttt{netem}. Measurements use \texttt{ping -c <N> <destination>} and \texttt{iperf3 -c <destination> -R -t <seconds>}. The runner parses output, writes run-scoped artifacts, verifies routes/qdiscs where supported, and removes only project-owned run resources.

\subsection{RL policy settings and complete policy summary}
\label{sec:rl-formulation}

Actions are paths A and B. Each agent invocation starts from initialized synthetic path-A metrics; thereafter only Q-learning uses state comprising the prior measured RTT (low below 45 ms, otherwise high), loss (none below 1\%, otherwise loss), throughput (high at or above 16 Mbps, otherwise low), and current path, then updates its Q-table from measured reward. The heuristic selects the path minimizing configured delay plus four times configured loss in the known phase; fixed A/B always select their named paths. Reward is:
\begin{verbatim}
R = throughput_mbps - 0.05 * rtt_ms
    - 0.50 * packet_loss_percent
\end{verbatim}
In Phase 1, A has (5 ms, 0\%, 20 Mbps) and B has (30 ms, 4\%, 12 Mbps); Phase 2 swaps these conditions. The schedule is ordered, not randomized. Q-learning uses $\alpha=0.35$, $\gamma=0.85$, $\epsilon=0.18$, and seed 20260722. Its completed rows 1--4 were migrated; rows 5--20 used a newly initialized \texttt{QLearningAgent}, with no restoration or replay of the earlier Q-table. Each policy has 20 valid descriptive Docker measurement rows, but the Q-learning rows are not one uninterrupted learning trajectory. Failed/retried checkpoints remain in evidence and are excluded from valid-row statistics.

\subsection{Reproduction boundary}
\label{sec:reviewer-reproduction}

The final code/evidence publication is GitHub main commit \href{https://github.com/Mochi486/Digital-Twin/tree/09a14859bb17e36d892c2145e129128525687229}{\texttt{09a14859bb17}}; the link resolves the full immutable SHA. The snapshot includes the dissertation-primary balanced bandwidth cohort listed in Table~\ref{tab:appendix-inventory}. In a fresh WSL clone with Docker and Python available, the shortest supported path is:

\begin{verbatim}
bash scripts/reviewer_setup.sh
bash scripts/reviewer_dashboard.sh
# open http://127.0.0.1:8765
\end{verbatim}

The setup script creates \path{.venv-wsl311}, installs the declared requirements, builds \path{my-iperf-tc}, and runs the 69 unit tests. The start script launches \path{dashboard/interactive_server.py} on port 8765. Reviewers may inspect retained evidence and use all three small topologies in dry-run mode; real Dashboard execution is intentionally direct-only. Reviewer-readiness checks post-date the original evidence sealing and are not additional formal observations. The separately retained balanced bandwidth cohort was added as a later supplementary replication and does not alter or rerun the sealed delay, loss, Germany50, AI, or RL matrices. A future independent replication should retain host/kernel/Docker versions, image digests, stdout/stderr, and resource utilization, then compare new results without overwriting the evidence used here.
